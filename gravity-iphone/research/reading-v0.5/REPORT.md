# v0.5「読まれない」の調査

2026-10-16。対象：配布済みv0.5（製品ソース b2d18fc、配布記録04c9948）。製品のコードは変更せず、実際の `ChatLayoutAnalyzer` / `CommentDetector` / `FreshSpeechQueue` を公式Swift5.7.2 Linuxで実行した。入力は合成画像と模擬OCR行であり、GRAVITY実機の記録ではない。

## 実行して再現できた取りこぼし

| 条件 | 本文OCR行 | 発言として抽出 |
|---|---:|---:|
| アイコン・認識済みの名前・本文 | 1 | 1 |
| 同じ画像で、名前のOCR行だけ欠落 | 1 | 0 |
| 名前の認識確度0.19 | 1 | 0 |
| 名前の認識確度0.20 | 1 | 1 |
| 名前領域の高さが画面高の6%（装飾や行結合を模擬） | 1 | 0 |
| 本文右端が画面幅の81%に達する | 1 | 0 |

名前の読み取りを外せば単純に全て解決するとは言えないが、本文が正しく取れていても名前の欠落だけで落ちることは確認できた。認識閾値・配置の閾値が発言全体の可否を決めている。本文の右端は80%を越えると除外されるため、幅の広い吹き出しでも取りこぼし得る。

## 発言として抽出できても、新着判定で無音になる

いずれも本文は認識できたものとして、実際の新着判定へ入力した。

- 既存A → A＋新着B → A＋B：Bを1回出力する。比較の基準となるAが残る場合は通る。
- 「こんにちは」→「こんばんは」→「こんばんは」→「またね」→「またね」：5画面を与えても読み上げ候補は0件。古い本文との重なりがないと、新画面を履歴として採用するため。
- 空 → 空 → 最初の「こんばんは」→「こんばんは」：候補0件。最初の非空画面は常に基準画面になる。
- 待機列へ追加してから9秒後に取り出すと破棄される。8秒の鮮度制限による仕様であり、単独の不具合ではない。

これらは現在の安全側の設計に起因する。単純に「全て新着」とするとルーム切替・過去ログ移動で履歴を読み始めるため、その置き換えは行っていない。画面変化、画像・本文の出現位置、スクロールや切替の扱いを含めた判定が必要。

## 音声出力の調査

現在の `PrivateSpeaker` は開始時に `AVAudioSession.setActive(true)` を呼ぶが、音声割り込み通知を監視していない。内部の `active` はアプリ開始／停止に連動するだけで、OSによる音声セッション無効化には連動しない。割り込み後の再開処理もない。

Apple公式資料では、割り込み開始時には音声セッションが非アクティブになると説明されている。また、`AVSpeechSynthesizer.usesApplicationAudioSession = false` で、音声・割り込み・他音源とのミックス等をOS側の別セッションに管理させる方法がある。

- [音声割り込み通知](https://developer.apple.com/documentation/avfaudio/avaudiosession/interruptionnotification)
- [割り込みの処理](https://developer.apple.com/documentation/avfaudio/handling-audio-interruptions)
- [音声合成のセッション管理](https://developer.apple.com/documentation/avfaudio/avspeechsynthesizer/usesapplicationaudiosession)

**GRAVITYが実際に音声割り込みを起こしているか、OS管理の方式で改善するかは未検証。** ソースと公式仕様の不一致・未対応は確認したが、実際の音が出ない原因と断定できない。iOS26以前向けの割り込みAPIと、将来の新APIを混同しない。

## 診断画面の限界

静止画の診断では、抽出済み本文をそのままホストアプリで試し読みする。配信時に通る新着判定を通さず、音声が動くプロセスも配信拡張とは異なる。したがって「静止画の文字が出た」「試し読みが聞こえた」だけでは、配信中に発声することを検証できない。

現行ログにはOCR行数・抽出数はあるが、新着候補数・音声待機数・発声開始／完了・割り込み数がない。実機で無音になった層を一意に特定できないことも、調査を長引かせている。

## 修正を進める順序

1. 名前のOCR成功を必須条件から外し、名前らしい画像領域の位置を補助証拠として利用する。画像に対応しない本文・座席・入力欄・キーボードの除外は維持する。
2. 配信で、OCR → 発言抽出 → 新着 → 音声待機 → 発声イベントの件数を追えるようにする。本文・名前・画面はログに保存しない。
3. 古い本文との重なりだけに依存しない新着検出を検証する。履歴移動やルーム切替を新着扱いしない回帰ケースも必要。
4. 音声はOS管理セッションと割り込み復帰を切り分けて確認する。通知や発声イベントが来ても、聞こえた証明にはしない。

新しい修正版としては未配布。今回の成果物は原因調査であり、実機の問題解消を意味しない。

## 再実行

```
cd gravity-iphone
bash scripts/investigate-reading.sh
```

`results.json` は今回の出力。名前欠落等で0件になる挙動を観測・検査するもので、その挙動を望ましい仕様として保証するテストではない。
